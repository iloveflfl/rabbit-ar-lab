# AR 좌표계와 보정

모든 배치값은 `apps/web-ar/src/ar/sceneLayout.ts` 한 파일에 있다.

## 좌표계

- 포스터 로컬: 원점 = 포스터 중심, x → 오른쪽, y → 위, **z → 포스터에서 관람객 쪽**
- 단위: 포스터 가로 폭 = 1 (실물 0.594 m). 세로 = 841/594 ≈ 1.4158. `CM`, `METER` 상수로 실물 길이를 쓴다.
- 정규화 좌표 (u, v): 왼쪽 위가 (0, 0), 오른쪽 아래가 (1, 1). `uvToLocal` / `localToUv` 로 바꾼다.

z 의 부호는 추측하지 않고 확인했다: MindAR 의 `Controller._glModelViewMatrix` 와 postMatrix 를 따라가면
앵커의 +z 가 카메라 쪽이고, 모의 카메라에서 z > 0 인 소품이 포스터 앞으로 나와 시차가 생기는 것을 봤다.
실기기에서도 옆으로 움직였을 때 토끼·그래프가 포스터보다 **더 많이** 움직여 보이면 맞는 것이다.

## 깊이 계층 (`Z`)

| 층 | z | 실물 |
|---|---|---|
| 덮어쓰는 2D 포스터 | 0.003 | 약 2 mm |
| 강조 테두리·그림자 | 0.006 | |
| 그래프 바닥 | 0.012 | |
| 3D 소품 | 0.03 ~ 0.13 | 2 ~ 8 cm |
| 토끼 2D 평면 | 0.185 | 약 11 cm |
| 떠다니는 입자 | ~0.37 | 최대 22 cm |

깊이 센서가 없으므로 현실의 사람·물건 뒤로 가려지는 표현(occlusion)은 하지 않는다.

## 이미지 타깃

`TARGETS` 에 세 개가 있고, `.mind` 파일 안의 순서와 같아야 한다.

| id | 영역 (v) | 용도 |
|---|---|---|
| full | 0 ~ 1 | 포스터 전체가 보일 때 (1 m 이상) |
| upper | 0 ~ 0.545 | 가까이서 위쪽만 보일 때 |
| lower | 0.535 ~ 0.925 | 가까이서 아래쪽만 보일 때. QR 이 붙는 결론 띠는 뺐다 |

부분 타깃으로 잡히면 `targetToPoster()` 가 주는 이동·배율로 포스터 전체 좌표계로 옮긴다
(`layout.test.ts` 가 이 변환을 검사한다). 한 번에 하나만 추적한다(`maxTrack: 1`).
지금 쓰던 타깃이 살아 있으면 계속 쓰고, 놓치면 다른 타깃으로 옮긴다.

타깃을 다시 만들어야 하는 경우: 포스터 인쇄본이 바뀌었을 때, `TARGETS` 를 바꿨을 때.
절차는 `scripts/compile_target.md`.

## 추적 방식 (2026-11-18 개정)

처음 버전은 MindAR 의 자세를 그대로 썼고, 실기기에서 "오차가 크고 부들부들 떨린다"는 결과가 나왔다. 원인은 둘이었다.

1. **카메라 모델**: MindAR 는 카메라 세로 시야각을 45° 로 고정 가정한다. 실제 폰은 60° 안팎이라, 비스듬히 볼수록 자세가 틀어진다.
2. **추적 해상도**: MindAR 는 포스터 폭을 128 픽셀로 줄인 그림에서 정수 픽셀 단위로 맞춘다. 한 픽셀이 포스터 위 4.6 mm 라, 프레임마다 자세가 그만큼 튄다.

지금은 MindAR 를 "특징점 찾기·따라가기"에만 쓰고 나머지는 직접 한다 (`ar/mindarBridge.ts`).

| 단계 | 하는 일 | 파일 |
|---|---|---|
| 추적 해상도 | 256 픽셀 그림 사용 (한 픽셀 2.3 mm) | `mindarBridge.ts` |
| 탐색 시작점 | 직전 자세가 아니라 센서로 예측한 "지금" 자세에서 찾는다 → 빨리 돌려도 덜 놓친다 | `mindarBridge.ts` |
| 자세 풀이 | 실제 초점거리로 재투영 오차 최소화 + 이상점 제거 | `pose/planarPose.ts` |
| 초점거리 | 비스듬히 본 프레임들을 모아 스스로 보정하고 기기에 저장 | `pose/filters.ts` `FocalCalibrator` |
| 시간 방향 | 아래 두 경로 중 하나 | `pose/filters.ts` |

### 경로 1 — WebXR (Android Chrome + ARCore)  `ar/xrView.ts`

ARCore 가 카메라 영상과 자이로·가속도계를 융합해 폰의 위치와 각도를 실제 길이 단위로 추적한다.
우리는 포스터가 세계의 어디에 붙어 있는지만 추정한다 (`WorldPosterEstimator`).

- 포스터는 움직이지 않으므로 여러 프레임의 관측을 모아 하나의 자세로 굳힌다 → 떨림이 사라진다.
- 굳은 뒤에는 포스터가 화면 밖으로 나가거나, 가려지거나, 아주 가까이 다가가도 콘텐츠가 제자리에 있다.
- 카메라가 조금 움직이면 시차로 포스터의 실제 크기를 알아낸다 → A1 이 아닌 크기로 인쇄했거나 모니터에 띄워도 깊이가 맞는다.
- 초점거리는 브라우저가 알려 주는 실제 값을 쓴다.

필요 조건: `immersive-ar` + `camera-access`(카메라 영상 접근) 지원. 없으면 경로 2 로 내려간다.
영상이 5초 동안 안 오거나 25초 동안 한 번도 인식하지 못해도 경로 2 로 내려가고, 그 기기에서는 다음부터 경로 2 로 바로 간다
(`?xr=1` 로 다시 시도, `?xr=0` 으로 강제로 끔).

**이 경로의 WebXR 호출부는 실기기에서 아직 실행해 보지 못했다.** 추정기 자체는 단위 테스트와 `?mode=simworld` 로 확인했다.

### 경로 2 — 카메라 영상 + 자이로 (iOS Safari, 인앱 브라우저 등)  `ar/tracker.ts`

ARCore 가 없으면 폰의 위치는 영상에서만 알 수 있다. 하지만 **회전**은 방향 센서로 정확하고 빠르게 알 수 있다.

- 세계 기준으로 보면 포스터의 방향은 폰을 아무리 돌려도 변하지 않는다. 이 값을 천천히 평균하면 영상 관측의 잡음이 사라진다.
- 그릴 때는 센서 속도(60 Hz 이상)로 즉시 따라간다. 센서의 느린 표류는 영상 관측이 계속 바로잡는다.
- 위치는 옆 방향(정확함)은 빠르게, 깊이 방향(흔들림)은 천천히 걸러 쓴다.
- 카메라 영상이 센서보다 얼마나 늦는지는 폰이 도는 동안 스스로 맞춘다.

가속도계를 두 번 적분해 위치를 구하는 방식은 쓰지 않는다. 몇 초 만에 수십 cm 씩 흘러서 쓸 수 없다.
위치까지 센서로 붙들려면 시각-관성 추적(ARCore/ARKit)이 필요하고, 그건 경로 1 이 맡는다.
iOS Safari 는 WebXR 을 지원하지 않으므로 아이폰은 항상 경로 2 다.

센서 권한(iOS)을 거부하면 자이로 없이 영상만으로 동작한다(적응형 평활).

### 조정값 (`ar/tracker.ts` 의 `TRACKING`)

| 값 | 기본 | 뜻 |
|---|---|---|
| `graceMs` | 450 | 추적을 놓친 뒤 센서만으로 자세를 이어 가는 시간 |
| `cameraLatencyMs` | 60 | 영상이 센서보다 늦는 시간의 시작값 (이후 자동 조정) |
| `maxRateDegPerSec` | 140 | 이보다 빨리 돌 때의 관측은 흐려져 있으므로 버린다 |
| `priorFovDeg` | 65 | 보정 전 시야각 가정 (긴 변) |

필터 세기는 `pose/filters.ts` 의 `GyroPoseFilter.update` 에 있다.

### 프레임이 끊기지 않게 (2026-11-18 추가)

실기기에서 "정확해졌지만 프레임이 떨어진다"는 결과가 나왔다. 원인은 추적 엔진(TensorFlow.js WebGL 연산 + 동기식 GPU 읽기)이
화면을 그리는 메인 스레드에서 매 프레임 돌고 있었기 때문이다. 포스터를 찾는 동안(검출)이 특히 무겁다.

| 바꾼 것 | 내용 | 파일 |
|---|---|---|
| 추적을 워커 스레드로 | 검출·추적·자세 풀이를 전부 워커에서 돌린다. 화면 스레드는 그리기만 한다. 결과는 그 프레임을 찍은 시각과 함께 돌아오므로, 늦게 도착해도 센서/세계 추적으로 정확히 맞춰 쓴다 | `trackerWorker.ts`, `trackerClient.ts` |
| 필요한 만큼만 추적 | MindAR 의 "매 화면 프레임" 루프를 버리고, 프레임을 줄 때만 한 번 처리한다. 세계에 고정된 뒤(WebXR)에는 초당 4번만, 포스터가 화면 밖이면 아예 돌리지 않는다 | `trackerClient.ts`, `xrView.ts` |
| 재검출 생략 | 포스터가 어디 있을지 알고 있으면 무거운 검출을 건너뛰고 예측 자세에서 바로 추적을 재개한다 | `mindarBridge.ts` |
| 카메라 영상 읽기(WebXR) | 두 프레임마다 읽던 것을 추적기가 요청할 때만 읽는다 | `xrView.ts` |
| 그리기 부하 | 토끼 캔버스는 초당 30번만 다시 그림, WebXR 은 기본 해상도의 80%, 영상 경로는 프레임이 밀리면 해상도를 단계적으로 낮춤(2 → 1.5 → 1.25 → 1) | `rabbitSprite.ts`, `tracker.ts` |

워커를 못 쓰는 브라우저(OffscreenCanvas WebGL 미지원 등)에서는 같은 코어를 메인 스레드에서 돌리되 주기를 낮춘다.
진단 상자의 `engine` 줄에 `worker` / `inline`, 프레임당 처리 시간, 검출·실패 횟수가 나온다. `?worker=0` 으로 워커를 끌 수 있다.

모의 카메라(데스크톱)에서 화면 프레임 간격의 중앙값:

| 상태 | 이전 | 이후 |
|---|---|---|
| 추적 중 | 38 ms (약 26 fps) | 12 ms (화면 주사율 그대로) |
| 포스터를 찾는 중 | 74 ms (약 14 fps) | 12 ms |

부작용: 영상 경로(경로 2)에서는 관측이 워커를 거쳐 조금 늦게 도착하므로, 손이 옆으로 미세하게 흔들릴 때의 잔떨림이
모의 측정에서 0.9 px → 약 1.8 px (720 px 폭 기준)로 늘었다. 세계 고정(경로 1)은 0.2 px 그대로다.
데스크톱 수치이며, 폰에서 워커가 실제로 얼마나 걸리는지는 진단 상자로 확인해야 한다.

### 프레임 더 올리기 (2026-11-18, 2차)

| 바꾼 것 | 이유 |
|---|---|
| UI 의 배경 블러(`backdrop-filter`) 제거 | 자막·채팅 패널이 화면의 40% 를 덮는데, 그 뒤의 카메라 영상이 매 프레임 바뀌므로 매 프레임 다시 흐리게 만들어야 했다. 모바일 GPU 에서 가장 비싼 축이다. 조금 더 불투명한 단색으로 바꿨다 |
| MSAA 끄기 (화소 밀도 2 이상인 화면, WebXR 은 항상) | 폰 화면에서는 차이가 거의 안 보이는데 채우는 비용이 크다 |
| WebXR 카메라 영상 비동기 읽기 (PBO + fence) | `readPixels` 를 배열로 바로 받으면 GPU 가 끝날 때까지 화면 스레드가 멈춘다. PBO 로 받아 다음 프레임들에서 꺼낸다 |
| WebXR 그리는 영역 자동 조절 (`requestViewportScale`) | 프레임이 50 아래로 떨어지면 0.1 씩 줄이고(최소 0.55), 여유가 8초 이어지면 되돌린다. 버퍼를 다시 만들지 않아 끊김이 없다. 브라우저의 권장값도 반영 |
| 화면이 밀리면 추적 주기를 늘림 | 추적 스레드도 같은 GPU 를 쓴다 |
| 카메라 60fps 요청 (영상 경로) | 카메라 영상 자체가 초당 30장이면 그 이상으로는 부드러워질 수 없다. 기기가 지원하면 60장으로 받는다 |
| 토끼 캔버스 해상도 ↓, 포스터 텍스처 이방성 필터 8 → 4 | 업로드·샘플링 비용 |

넘을 수 없는 한계: WebXR(ARCore) 의 카메라 영상은 보통 초당 30장이고 렌더는 60 이다. 3D 콘텐츠는 60 으로 부드럽게 움직여도
배경 영상은 30 으로 보인다. 이건 브라우저와 ARCore 가 정하는 값이라 바꿀 수 없다.

진단 상자: `fps` 줄의 `slow a/b` 는 25ms 넘게 걸린 프레임 수 / 전체, `@x` 는 지금 그리는 해상도 배율이다.
영상 경로의 `camera` 줄은 카메라가 실제로 주는 초당 프레임 수, WebXR 의 `read` 줄은 비동기 읽기가 몇 프레임 뒤에 끝나는지다.

### 회귀와 수정: "움직이면 포스터와 따로 논다" (2026-11-18)

프레임 개선 직후 실기기에서 "움직이면 덮개가 포스터에서 떨어져 따로 논다"는 결과가 나왔다.
원인: 세계 고정 추정이 **관측 10개만 모이면 "고정됐다"고 보고 보정 주기를 초당 4~5회로 낮췄다.**
그 시점의 추정은 "지금 보는 방향에서만" 맞을 수 있다(크기·거리는 카메라가 움직여 시차가 생겨야 정해진다).
그래서 움직이기 시작하면 어긋나는데, 보정이 드물어 어긋난 채로 남았다. 모의에서 450 px 오차가 8초 넘게 유지되는 것으로 재현했다.

고친 것

- 추정에 **수렴(converged)** 단계를 따로 둔다: 관측 40개 이상 + 시차 정보가 충분할 때만 수렴으로 본다.
- 수렴 전, 또는 폰이 움직이는 중에는 초당 20~25회로 촘촘히 관측한다. 수렴했고 가만히 있을 때만 느슨하게 한다.
- 수렴 전에는 전체 평균이 아니라 **가장 최근 관측**에 맞춰 그린다 → 움직이는 동안에도 포스터를 덮은 채로 따라간다.
- 관측이 추정과 연달아 어긋나면(8회) 추정을 버리고 다시 모은다. 최근 관측과 안 맞는 오래된 키프레임은 버린다.
- "포스터가 화면 밖이면 추적 중단"은 수렴한 뒤에만 하고, 그래도 1초에 한 번은 확인한다.
- 예측 자세에서 못 찾으면 바로 다음 프레임에서 검출을 돌린다.
- 영상 경로: 브라우저가 프레임별 촬영 시각을 알려 주면(`requestVideoFrameCallback` 의 `captureTime`) 그 시각으로 센서를 맞춘다.
  워커로 옮기면서 프레임을 집는 시점이 비동기가 됐기 때문에, 추정 지연값보다 이쪽이 정확하다. `?vfc=0` 으로 끌 수 있다.

모의 측정 (최대 꼭짓점 오차, 720×1280 픽셀, 옆으로 계속 움직이는 동안)

| 상황 | 수정 전 | 수정 후 |
|---|---|---|
| A1 포스터, 세계 고정 | — | 1~3 px |
| 절반 크기 포스터, 세계 고정 | 450 px 가 8초 넘게 유지 | 처음 2~3초 30~65 px → 이후 1~15 px (추정 폭 30.9 cm, 참값 29.7) |
| 영상+자이로 경로 | — | 4~13 px, 놓침 0% |

진단 상자의 `world` 줄에 `converging` / `converged` 와 `resets`(추정을 버린 횟수)가 나온다.

### 화면에서 진단하기

주소 끝에 `?debug=1` 을 붙이면 왼쪽 위에 진단 상자가 뜬다(배포본에서도 동작).

```
mode   webxr (ARCore) / video
fov    추정 시야각 (prior = 가정값, calibrated = 보정됨)
gyro   on/off, 회전 속도
sync   frame clock = 프레임 촬영 시각 사용 / guess = 지연값 추정
track  추적 주기, 인라이어/점 수, 재투영 오차(px)
engine worker/inline, 프레임당 처리 시간(ms), 검출 횟수, 실패 횟수
fps    화면 주사율과 그리는 해상도 배율
innov  관측과 추정의 차이 (각도, 거리 비율) — 가만히 들고 있을 때 0.3° / 0.5% 아래면 정상
width  (WebXR) 추정한 포스터 실제 폭
```

문제가 있을 때 이 상자의 값을 알려 주면 원인을 좁힐 수 있다.
비교용 스위치: `?gyro=0` (자이로 끔), `?cal=0` (초점거리 보정 끔), `?lat=80` (지연 고정), `?xr=0` (WebXR 끔).

## 모의 카메라 측정값 (2026-11-18, 720×1280 영상 픽셀)

손떨림(회전 ±0.25°, 위치 ±2 mm)을 넣은 가상 카메라. error = 네 꼭짓점 오차의 평균, jitter = 그 오차가 시간에 따라 흔들리는 정도.

| 조건 | 이전 (최대 꼭짓점 오차) | 경로 2: 영상+자이로 error / jitter | 경로 1 의 추정기(모의 세계 추적) error / jitter |
|---|---|---|---|
| 정면 1.15 m | 4.8 | 1.6 / 0.9 | 1.2 / 0.2 |
| 좌우 30° | 24 | 1.4 / 0.8 | 1.2 / 0.3 |
| 0.8 m (포스터가 화면을 넘침) | 42 | 2.7 / 1.9 | — |
| 0.6 m | 22 | 3.3 / 2.6 | 2.5 / 0.6 |
| 포스터를 가림 | 사라짐 | 사라짐(0.45초 뒤) | 유지 2.6 / 0.2 |
| 55° (인식 한계 밖) | 사라짐 | 사라짐 | 유지 0.8 / 0.3 |

- 초점거리 자동 보정: 65° 가정에서 시작해 57.4~59.5° 로 수렴 (참값 58°).
- 절반 크기 포스터: 추정 폭 31.4 cm (참값 29.7 cm).
- 이전 값은 측정 방식이 달라(최대값) 직접 비교는 대략적이다.

**이 숫자들은 모의 환경의 것이다.** 실제 폰에는 렌즈 왜곡, 롤링 셔터, 자동 초점, 조명, 인쇄 반사가 있고
ARCore 의 실제 정확도도 환경에 따라 다르다. 실기기 결과는 DEVICE_VERIFICATION.md 에 적는다.

## 새 포스터의 패널과 3D 자리

`PANELS` (영역 9개)와 `SLOTS` (3D 소품이 들어갈 자리)를 포스터 그림(`stage/posterArt.ts`)과
3D 소품(`stage/props.ts`)이 같이 읽는다. 자리를 옮길 때는 이 표만 바꾸면 그림과 소품이 함께 움직인다.
